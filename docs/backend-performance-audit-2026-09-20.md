# 第三轮审计：后端服务性能深审

日期：2026-09-20（2.5.0 运行中）
前两轮审计覆盖了正确性与生产就绪；本轮专注后端服务性能：全端点延迟画像、并发压测、SQLite 查询计划、序列化与持久化微基准、内存与事件循环行为。全部结论来自当日在运行服务与真实库副本上的实测。

## 1. 审计方法

1. 顺序延迟画像：14 个代表端点各 20 次采样（预热后取 min/avg/p90/max）。
2. 并发压测：两个重端点各按 10/30/60 并发梯度压 3 轮共 300 请求，测吞吐与延迟退化。
3. SQLite：只读副本上对 9 条热查询做 EXPLAIN QUERY PLAN 加各 50 次计时。
4. 微基准：真实库副本加真实 resolver 上测 serialize/loadSessions/gzip/scrypt。
5. 进程内存与日志增长复查。

## 3. 并发压测（本轮核心发现）

| 并发度 | bp/bootstrap | character-stats |
| --- | --- | --- |
| c=10 × 3 轮（30 请求） | wall 1039ms，avg 697ms | wall 48ms，avg 35ms |
| c=30 × 3 轮（90 请求） | wall 3109ms，avg 2075ms | wall 120ms，avg 74ms |
| c=60 × 3 轮（180 请求） | wall 6246ms，avg 4146ms | wall 205ms，avg 131ms |

解读：
1. character-stats 近乎线性扩展（缓存命中后单次 3ms，60 并发下 131ms），事件循环健康。
2. **bp/bootstrap 是 CPU 密集型事件循环阻塞点**：单次约 35ms 的同步计算不随并发分摊，60 并发下事件循环被连续占用 6.2 秒，期间全部请求（含 SSE 心跳、OBS 命令转发）排队等待。触发场景：部署重启后缓存冷、多页面同时刷新、OBS 源批量重连。
3. 在 2 核服务器上单核性能弱于本开发机，同等并发的每请求延迟会更高，但排队行为相同。

## 4. 瓶颈定位（微基准实证）

对真实库副本（57 会话、3308 条历史）加真实 resolver 逐会话计时：

1. serialize 平均 0.72ms，最重会话（90 条历史）1.94ms；成本随历史长度线性增长（每条历史自带整会话快照，clone 为 O(历史)）。
2. **57 会话全量序列化 ≈ 41ms，与 bp/bootstrap 实测的 35 到 40ms 精确吻合**——bootstrap 的成本就是逐会话 serialize 的累加。
3. loadSessions 全量重载平均约数 ms（57 行加 741 槽位加 47 结果），不是瓶颈。
4. gzip：600K JSON 载荷异步压缩约 10ms 内完成，2 核线程池可承受。

## 5. SQLite 查询计划审计

9 条热查询全部索引覆盖或亚毫秒：effective_sessions CTE 0.003ms（MATERIALIZE 后索引联接）、BP 历史按会话 0.003ms（idx_bp_history_session）、未读水位 0.005ms、通知联表 0.006ms、频道列表 0.029ms、审计分页 0.171ms（索引顺序扫描）、BP 会话全量加载 0.114ms（57 行全表扫描属预期）。EXPLAIN 发现的 SCAN 均为小表全扫或索引顺序扫描，无缺失索引导致的实际性能问题。
结论：**数据库不是瓶颈**，与第二轮审计的结构结论一致。

## 6. 其他后端成本实测

1. scrypt 密码哈希 27.2ms/次：仅登录时执行，属刻意设计（防爆破成本），可接受。
2. SSE 心跳：呈现心跳约 2.8KB/秒/客户端，10 客户端约 0.23Mbps，无压力。
3. 登录失败限速的内存 Map 存在理论无限增长（每个新账号加 IP 组合一条目，无过期清扫，仅成功与到期读取时移除）：单机场景条目极小，列为 P3 微观债。
4. sendJson 的 gzip 每次请求实时压缩无结果缓存：no-store 语义下正确，CPU 成本实测可承受；若未来 CPU 紧张可加预压缩缓存。

## 7. 发现与建议（按优先级）

| 级别 | 发现 | 建议 | 工作量 |
| --- | --- | --- | --- |
| P1 | bp/bootstrap 单次约 35ms 同步阻塞事件循环，并发下线性排队 | 加短 TTL 结果缓存（3 到 5 秒，revision 变更即失效），或 bootstrap 不内嵌完整 history（历史走独立端点） | 半天 |
| P2 | serialize 的 O(历史) 全量 clone | 与上条一并处理：会话级序列化缓存，revision 变更失效 | 同上 |
| P2 | operations/terminal 24ms（10 秒轮询一次） | 可接受；如要优化需先剖析其内部系统信息采集 | 观察 |
| P3 | node:sqlite 语句未预编译缓存（每次 prepare） | 微观收益，数据量增长后再议 | 已在路线图批次 8 |
| P3 | 登录失败 Map 无过期清扫 | 加定时清扫或容量上限 | 10 分钟 |

## 9. 结论

后端服务的常规读取性能健康（除 bp/bootstrap 外全部 6ms 以内），数据库经查询计划实证不是瓶颈，内存与事件循环在压测下行为正常。**唯一的实质性优化点是 bp/bootstrap 的逐会话序列化累加**：加会话级序列化缓存或 bootstrap 剥离 history，即可把最重接口降到 5ms 级并消除并发排队。该项连同路线图批次 3（路由表化）建议在下一次专项会话执行。
